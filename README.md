# Pi Cloud

A private, recoverable chat application. `harness/` contains the Solid 2 SSR interface, server functions and durable PostgreSQL writer as one component. There is no TUI, standalone Web service, shared contract package or public REST API. Authorized conversations continue after the browser disconnects.

- **Harness** (`pi-cloud-harness`): request middleware uses OIDC authorization code + S256 PKCE, validates signed access tokens against the configured issuer and API audience, and checks same-origin POSTs for server functions. Only opaque HttpOnly, SameSite cookies reach the browser. The expiring session record stores the access token encrypted with the random browser session handle; the database holds only its hash and ciphertext. Users can read or change only their own conversations. `src/rpc.ts` owns the typed Solid server functions, `schema.ts` validates their inputs with ArkType. Kysely queries run on the same PG session as the writer lock. A lost writer observes accepted tool calls rather than replaying unknown effects.
- **Controller** (`pi-cloud-sandbox-controller`): a private Go service managing disposable Pods, expiring leases and optional per-user writable PVCs. It does not run commands. The binding includes the effective grants, claim UID, image digest and configuration. Idle eviction does not delete the PVC.
- **Sandbox** (`pi-cloud-sandbox`): a TypeScript worker and a native Linux Landlock/seccomp guard. Public Web egress is opt-in through a Unix socket; the worker pins validated public IPv4 addresses. This is not VM isolation.

Set `PUBLIC_ORIGIN`, `OIDC_ISSUER`, `OIDC_AUDIENCE`, `OIDC_CLIENT_ID`, `DATABASE_URL`, `MODEL_ID`, `MODEL_BASE_URL` and optional `MODEL_CHOICES` on the harness. Register only the exact `/callback` URI, limit the API audience to admitted users, and configure `sandbox#execute`, `sandbox#persistent-volume`, `sandbox#egress-web` as separate Keycloak permissions. `CONTROLLER_URL` and `CONTROLLER_KEY` enable tool execution. The controller needs the same internal key, `SANDBOX_IMAGE` by digest, optional `STORAGE_CLASS`, `VOLUME_SIZE`, `RUNTIME_CLASS`, `PROFILE_REVISION`, `IDLE_SECONDS` (600 by default). It needs Pod get/list/create/patch/delete and PVC get/create in a dedicated namespace. Keep controller and workers private, with authenticated workload transport and enforced ingress policy. Only the harness handles browser traffic; production requires HTTPS. Session expiry requires signing in again.

The sandbox does not impose its own process-count limit. A Linux UID may be shared with unrelated Pods, so the guard leaves the inherited `RLIMIT_NPROC` unchanged. CPU and memory limits do not guarantee protection against node PID exhaustion.

## Local verification

Use Node 26, Go as pinned in `sandbox-controller/go.mod`, a C compiler and Linux with Landlock and seccomp. In `harness/` and `sandbox/`: `npm ci && npm run check && npm test`. Build the full-stack app with `npm --prefix harness run build`; check browser-only content and the Brotli JS budget with `node harness/check-bundle.ts`. From `sandbox-controller/` run `go test -race ./... && go vet ./...`.

For browser acceptance install dependencies and Chromium under `harness/e2e/`. Build the controller fixture with `go test -c -o /tmp/pi-controller-fixture` in its component directory. Set `CONTROLLER_FIXTURE` to that binary, `KC_HOME` to a disposable Keycloak 26.4.7 distribution and `JAVA_HOME` to Java 21; run `npm --prefix harness/e2e test`. The suite runs the production build on loopback with real OIDC, temporary PostgreSQL, the Go controller against a simulated Kubernetes API, a real worker and a fake model. It checks authorization, tool streaming, writer recovery and mobile Lighthouse budgets on an authenticated conversation (not the sign-in page). No production credentials needed.

CI builds native arm64 candidates from the repository context, tests them and publishes on main. Product CI has no cluster credentials. MicroVM isolation, Code Mode and database-primary failover qualification remain future work.
