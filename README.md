# Pi Cloud

A private, recoverable chat application. One repository builds three images. `harness/` contains the Solid 2 app and durable writer, `sandbox-controller/` owns Kubernetes resources, and `sandbox/` executes commands. Component tests live with their code; `acceptance/` exercises the browser and the three components together. There is no TUI, standalone Web service or public REST API.

- **Harness** (`pi-cloud-harness`): `web/` owns SSR and typed RPC; `identity/` handles OIDC with S256 PKCE and opaque secure sessions. `conversations/` owns conversation behavior, and `tools/cmd/` coordinates authorization and dispatch. Session storage uses a connection pool; journal, conversation ownership and the command ledger are written on the PostgreSQL session holding the writer lock. Creating a conversation and its owner index is atomic. After writer loss, harness observes the original sandbox rather than redispatching a command with uncertain effects.
- **Controller** (`pi-cloud-sandbox-controller`): a private Go service managing disposable Pods, expiring leases and optional per-user writable PVCs. It does not run commands. The binding includes the effective grants, claim UID, image digest and configuration. Idle eviction does not delete the PVC.
- **Sandbox** (`pi-cloud-sandbox`): Go `sandboxd` manages each call's lifetime, output, deadline and cancellation. The native C guard applies Landlock/seccomp before executing the shell; setup failure does not fall back to an unrestricted shell. Commands use the deployment's existing network directly. Pi does not block private networks, metadata endpoints, or loopback destinations. This is not VM isolation.

Set `PUBLIC_ORIGIN`, `OIDC_ISSUER`, `OIDC_AUDIENCE`, `OIDC_CLIENT_ID`, `DATABASE_URL`, `MODEL_ID`, `MODEL_BASE_URL` and optional `MODEL_CHOICES` on the harness. Register only the exact `/callback` URI, limit the API audience to admitted users, and configure `sandbox#execute` and `sandbox#persistent-volume` as separate Keycloak permissions. `CONTROLLER_URL` and `CONTROLLER_KEY` enable tool execution. The controller needs the same internal key, `SANDBOX_IMAGE` by digest, optional `STORAGE_CLASS`, `VOLUME_SIZE`, `RUNTIME_CLASS`, `PROFILE_REVISION`, `IDLE_SECONDS` (600 by default). It needs Pod get/list/create/patch/delete and PVC get/create in a dedicated namespace. Keep controller and workers private, with authenticated workload transport and enforced ingress policy. Only the harness handles browser traffic; production requires HTTPS. Session expiry requires signing in again.

The sandbox does not impose its own process-count limit. A Linux UID may be shared with unrelated Pods, so the guard leaves the inherited `RLIMIT_NPROC` unchanged. CPU and memory limits do not guarantee protection against node PID exhaustion.

Release the three components together. The new dispatch protocol requires a short-lived controller ticket bound to the Pod UID, worker boot ID, call ID and UTF-8 command digest. A worker management credential can observe and cancel but cannot issue a ticket. Ticket validation does not replace workload transport authentication or encryption. Pin the worker image by digest in the controller and plan the cutover so incompatible generations cannot receive new commands.

## Local verification

Use Node 26, Go as pinned in each `go.mod`, a C compiler, Python 3 and Linux with Landlock and seccomp. In `harness/`, run `npm ci && npm run check && npm test && npm run build`. From the repo root, run `node harness/test/check-bundle.ts`. In each Go module (`sandbox-controller/` and `sandbox/`), run `go test -race ./... && go vet ./...`.

For browser acceptance, install dependencies with `npm --prefix acceptance ci` and Chromium with `acceptance/node_modules/.bin/playwright install chromium`. Build the controller fixture (`go test -c -o /tmp/pi-controller-fixture ./cmd/controller` from `sandbox-controller/`) and the sandbox binaries (`go build -o /tmp/pi-sandboxd ./cmd/sandboxd` and `cc -Os -static guard/guard.c -o /tmp/pi-guard` from `sandbox/`). Set `CONTROLLER_FIXTURE`, `SANDBOXD` and `SANDBOX_GUARD` to the binary paths, `KC_HOME` to a disposable Keycloak 26.4.7 distribution, and `JAVA_HOME` to Java 21. Run `npm --prefix acceptance test` from the repository root. This exercises the production app build, real OIDC, temporary PostgreSQL, a simulated Kubernetes API, real sandbox binaries and a fake model. It does not establish real Kubernetes scheduling, PVC or workload transport behavior.

CI builds native arm64 candidates from the repository context, tests them and publishes on main. Product CI has no cluster credentials. See the [roadmap](ROADMAP.md) for future work.
